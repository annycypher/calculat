## Временное изменение
В `.htaccess` **временно закомментирован редирект `http -> https`**:
```apache
  # RewriteCond %{HTTPS} !=on
  # RewriteRule ^(.*)$ https://%{HTTP_HOST}/$1 [R=301,L]
```
Причина: сертификат на sweb ещё не выпущен, а сам sweb отдаёт `https -> http` — включённый
редирект дал бы петлю. **Включить обратно сразу после выпуска SSL** (и тогда же перезалить файл).

## Осталось
1. Дождаться обновления DNS-кэшей (реестр уже правильный: `ns1/ns2.spaceweb.ru`, `ns3/ns4.spaceweb.pro`).
2. Повторить выпуск SSL в панели sweb → затем вернуть редирект `http -> https` в `.htaccess`.
3. Через сутки — включить HSTS (строка в `.htaccess` уже подготовлена).
4. Фаза 2 (после переключения DNS): убрать `chunkload.js`, вернуть обычные `<script src>`,
   склеить шрифты в целые файлы, при желании — локальный OCR.
5. Удалить через 1–2 недели зону Cloudflare (пока она жива — это наш откат).

## Найденная и исправленная ошибка: петля редиректов на хабах
Первая версия правил содержала `RedirectMatch 301 ^/xxx/index\.html$ /xxx/`.
Nginx на sweb сам подставляет `index.html` при запросе папки, поэтому правило
срабатывало на `/converters/` и уводило на тот же адрес, а относительная цель за
прокси собиралась как `http://` — вместе с правилом `http -> https` получалась
петля (`ERR_TOO_MANY_REDIRECTS`) на `/converters/`, `/games/`,
`/calculators/finance/`, `/calculators/construction/`.

**Правила на будущее:** правил вида `^/xxx/index\.html$` в `.htaccess` быть не
должно, цели редиректов пишем полными `https://calc-doc.ru/...` (иначе лишний хоп
через http). Канонизацию держат `<link rel="canonical">` в самих страницах.

## Второй найденный и исправленный баг: отрицательные числа в счёте
При очень большом запасе виртуального времени headless-браузер в блоке статистики
показывал «-2 373 630 посещений» и «более -52 219 852 инструментов».
Причина в `js/home.js` → `countUp()`: прогресс зажимался только сверху
(`Math.min((t - t0) / dur, 1)`), а метку кадра даёт браузер — если она приходит
раньше `t0` (виртуальное время, фоновая вкладка, throttling), `p` уходил в минус и
куб `(1 - p)` давал огромные отрицательные значения.

**Исправлено:** `p` зажат в `[0; 1]`, значение дополнительно ограничено снизу нулём;
версия скрипта поднята до `js/home.js?v=4` (в кэше JS живёт 7 дней).

Цифра «1 посещение» за 15.09.2026 — это тестовый визит приёмки (обычный UA),
краулеры и `curl`/PowerShell в счётчик не попадают.

## Разбор ошибки 553 и проверка sitemap (16.09.2026)

### 1. Что это была за ошибка

`deploy.ps1` обрывался с `(553) File name not allowed`. Текст ошибки в PowerShell выглядел так:

```
ForEach-Object : Exception calling "GetRequestStream" with "0" argument(s):
"The remote server returned an error: (553) File name not allowed."
```

`GetRequestStream` — это момент, когда клиент отправляет команду `STOR` и ждёт ответ сервера,
то есть отказ пришёл от FTP sweb на попытку создать файл. Разбор
(`_game-test\ftp-error-test.ps1`, отчёт `shots\ftp-error.txt`):

| Проверка | Результат |
|---|---|
| Где оборвалась заливка | После 68 успешно отправленных файлов — на `js/calc-paint.js` (следующий за `js/calc-ndfl.js`) |
| Тот же файл, отправленный отдельно | ✅ 3 попытки из 3 — успешно (2 380 Б) |
| Бурст из 15 файлов подряд без паузы | ✅ 0 ошибок |
| `SIZE` по 51 файлу на сервере против локальных размеров | ✅ расхождений 0 — обрезанных файлов не осталось (при 553 поток данных не открывается вовсе) |
| Повторная полная заливка | ✅ прошла целиком, при этом `js/calc-deposit.js` и `privacy.html` потребовали по второй попытке |

Вывод: имя файла и путь корректны, это **разовый отказ FTP под плотным потоком запросов**
(он же был и в первый раз, 15.09, на другом файле). Ошибка настоящая, но невоспроизводимая
и без последствий для файлов.

### 2. Что было не так в самой реакции на ошибку

Опасной была не 553, а поведение скрипта: `$ErrorActionPreference = 'Stop'` и ни одного
`try/catch` вокруг отправки. Один отказ:

- обрывал заливку **в середине списка**, а не пропускал один файл;
- в первом прогоне (16.09) оставил на сервере старые корневые файлы — `index.html`,
  `header.css`, `styles.css` (папки уехали, корень нет). Внешне сайт остался целым и
  прежним, но при обрыве на пару десятков файлов позже на сервере оказался бы
  **новый HTML со старым CSS**;
- в логе печаталась только техническая ошибка, а `Готово (FTP)` не появлялось —
  при запуске не вручную это легко принять за успех.

### 3. Что исправлено в `deploy.ps1`

- `Send-FtpFile` — до 4 попыток на файл с растущей паузой (0,6 / 1,2 / 1,8 с) и пауза 40 мс
  между файлами;
- ошибка одного файла больше не обрывает заливку: он попадает в список неотправленных,
  остальные досылаются; в конце скрипт печатает этот список и возвращает **код 1**
  (успешная заливка — `Готово (FTP)`, код 0);
- текст ошибки стал разборчивым: из `WebException` достаётся ответ сервера
  (`FTP 553 File name not allowed`), а не только «Exception calling GetRequestStream»;
- то же поведение уже было в `upload-file.ps1` (точечная заливка, 3 попытки) — теперь
  оба скрипта одинаковы по надёжности.

Проверка после правки: полная заливка 16.09 прошла целиком — 115 файлов, `Готово (FTP)`,
код 0; двум файлам понадобилась вторая попытка, и оба уехали.
